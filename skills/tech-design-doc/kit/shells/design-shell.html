Where Relay decides

The send path, the plans and the support access of Relay, a notification platform.

→ The design in one page

Relay sends e-mail, SMS and push notifications for its tenants, the companies whose apps call it. This design decides where Relay checks each message, and what each plan and each support engineer sees.

1 The decision

What decides a message

  • Relay API checks every message before it queues it. A client app sees only its own calls. So no app can count the rate of its whole tenant, or apply an opt-out that a recipient made in another app.
  • The gateway checks the token and nothing else. It answers 401 before Relay API runs. Every other decision belongs to Relay API.
  • One versioned file holds the plans and the clusters. A new plan or a moved region changes the file, not the code. Every change needs a pull request that passes the tests.

Two rules decide what a reader sees. The plan of a tenant decides which dashboard tiers it sees (plans). The cluster of a support engineer decides which tenants they open (support access).

2 Plans: what a tenant sees

A plan buys tiers, not screens. The dashboard has eight blocks. A grant for each block and each plan leaves the product owner 40 cells to answer. So the blocks sit in three ordered tiers and three add-ons.

Table view
PlanTiersAdd-onsRegion access
FreeBasicnoneown region
TeamBasic, Analyticsnoneown region
BusinessBasic, AnalyticsSSO, Audit export (last 30 days)own region
EnterpriseBasic, Analytics, Raw logsSSO, Audit export, Dedicated IPall regions
PartnerBasic, Analytics, Raw logsSSO, Dedicated IPall regions

Each tier includes the tier below it, so a plan names one tier, never a list. The tiers follow what a reader can do with the data:

TierWhat it holdsWhat a reader can do with it
1 · Basicthe send API, the template editor, the status of each messageSend a message and see that it left.
2 · Analyticsdelivery, bounce and click rates, with CSV exportJudge a campaign. Every value is a rate, never one recipient.
3 · Raw logsevery API request and provider reply, kept 30 daysTrace one message. One export rebuilds the contact history of a tenant.

An add-on is a separate purchase that no tier carries: SSO, Audit export or Dedicated IP. Business gets the audit export for the last 30 days only.

A withheld block leaves no heading and no empty state, such as "No clicks yet". The dashboard looks the same whether the withheld data exists or not.

3 Support access: which tenants an engineer opens

The rule. A tenant carries one region: eu, us or apac. Each region sits in one support cluster. An engineer opens a tenant when one of their clusters holds its region.

No filter on messages. Scope is a property of the tenant, not of its messages. An engineer who opens a tenant sees all of its messages.

EntityWhat it isWhere it lives
Regionthe region of one tenant: eu, us or apacthe tenant record
Clusterthe regions that one support team covers: Atlantic holds eu and us, Pacific holds apacthe policy file, as clusters
Rolesupport.<cluster>, one per cluster, plus support.allthe identity provider

Three rules at the edges

  • A tenant with no region opens to nobody, except an engineer who holds support.all.
  • An absent tenant and a tenant out of scope get the same 404 body. So a reply never tells an engineer which tenants exist.
  • A moved region takes effect on the next request. The policy file changes, and no engineer signs in again.

4 Decisions the owners make

The product owner

  1. The plans. Does each plan in plans see the right tiers and add-ons? A change edits the policy file, not the code.

The security team

  1. Access in an incident. May an engineer open a tenant outside their clusters during an incident? A "yes" adds one role, support.incident, and one audit alert per use.

The legal team

  1. Message bodies and the model. May the subject-line model learn from message bodies? A "no" cuts a third feed in the data feeds.

5 Alternatives this design rejects

  1. Checks in each client app
    → Checks in Relay API.
    Reason: an app sees only its own calls, so it cannot apply a limit or an opt-out across its tenant.
  2. Hide screens by plan in the dashboard
    → Withhold the data before the dashboard renders.
    Reason: one field shows on up to five screens (what the dashboard shows).
  3. A permission service from the start
    → A policy file in the repository.
    Reason: five plans and two clusters fit in one reviewed file, and the tests cover all of it.

6 What the dashboard shows today

A place is one spot on a screen where a field shows. The figure counts the places of each field on each screen of the dashboard.

Three facts that break the simple approach

  • A withheld screen leaks. Withhold Logs, and the recipient address still shows in 3 of its 5 places, on Inbox and API. 17 of the 24 copies stay.
  • An empty block leaks a fact. "No clicks yet" tells a Free tenant that Relay counts its clicks. So the dashboard removes a withheld block and shows no empty state.
  • The API is a screen too. The recipient address, the delivery status and the API key reach it. So the same checks gate the JSON and the HTML.

7 The checks in Relay API

Two entries reach the same checks: the API send, POST /v1/messages, and the scheduled send. The checks run in a fixed order, and the first failure decides the reply.

StatusWhenWho answers
401the token is absent, expired or signed by another keythe gateway, before Relay API runs
403the tenant is suspendedRelay API
404the template does not existRelay API
429the tenant is over its rate limitRelay API, with Retry-After
204the recipient opted out: Relay API logs the message and sends nothingRelay API
503the provider of the channel is down: the app retries laterRelay API, with Retry-After
§7.1 · The send request

A client app sends one message per call. The Idempotency-Key header makes a retry safe: Relay API answers a repeated key with the first reply.

POST /v1/messages HTTP/1.1
Authorization: Bearer <token>
Idempotency-Key: 6f1c2a9e-3b7d-4c55-9a1e-0d2f7b8c4e11
Content-Type: application/json

{"template": "order-shipped", "channel": "email",
 "to": "ana@example.com", "data": {"order": "A-1042"}}

HTTP/1.1 202 Accepted
{"message_id": "msg_7Hq2Lw", "status": "queued"}

202 means queued, not delivered. The delivery webhook reports the outcome later.

8 Derived data and its feeds

An output can reveal a source without quoting it. So one rule decides every feed: a source feeds an output only if every reader of that output may see the source.

Each source carries a data class: Internal, Confidential or Personal. Each output carries the highest class that its readers may see. A feed whose source ranks above its output is cut.

Delivery receiptsInvoicesstaysthe delivered count is the billed count
Billing recordsInvoicesstaysthe plan, the price and the usage
  1. Opt-out list → AI subject-line suggestions: cut. The model must not learn from people who opted out. The training job drops every opted-out recipient before it reads a message.
  2. Message bodies → delivery analytics: cut. Analytics needs counts, not bodies. The analytics job reads the message metadata only.
  3. Delivery analytics → AI subject-line suggestions: kept. The analytics hold counts only, so the model may read them.

9 Tests that prove it

Every test runs on synthetic tenants, with a stub provider and no network.

  1. Canary test. Put a unique marker in every field of a test tenant. Render the dashboard for each plan. No marker of a withheld block may reach the HTML or the JSON.
  2. Same 404. An absent tenant and a tenant out of scope get byte-identical 404 bodies.
  3. One message per key. Send one request twice with the same Idempotency-Key. The stub provider receives one message.
  4. Policy snapshot. The repository holds the resolved grants of each plan, so a policy change shows as a diff in review.

10 Scheduled sends

A scheduled message waits in the scheduler until its send_at time. Then a worker sends it, and the provider reports the delivery back to Relay API.

Residual risk. A provider that ignores the key can still deliver a message twice after a timeout. Check each provider before you rely on the key.

11 What Relay runs

Relay runs no server. Seven managed services in one AWS account run all of it. The client apps of each tenant stay outside that account, and off the Relay bill.

ServiceThe part it playsIt bills for
Amazon API Gatewaythe entry point: checks the tokeneach request
AWS Lambdatwo functions: the Relay API and the delivery workerseach request and the compute time
Amazon SQSthe send queue: one job per messageeach request
Amazon SESthe e-mail sendereach e-mail sent
Amazon SNSthe SMS sendereach SMS sent, at a price for each country
Amazon S3the template storethe storage and each request
Amazon CloudWatchthe audit log: one line per requestthe log data it takes in and keeps

So the bill grows with the messages, not with the tenants. An idle tenant costs Relay almost nothing, and SMS is the most expensive channel.

12 Limits and operations

Relay API writes one audit line per request: the tenant, the outcome and the check that decided it. It never logs a message body or a recipient address.

Three numbers that limit the send path
202
Accepted, not delivered
Relay API answers when it queues the message. The delivery webhook reports the outcome later.
6,000/min
Default rate limit per tenant
A tenant over its limit in one minute gets 429 with Retry-After. The Enterprise plan can raise the limit.
24 h
Life of an idempotency key
A repeated key within 24 hours gets the first reply. After that, the same key starts a new message.
