Architecture diagrams — the full catalogue

Thirty-two types across six families: thirty-one diagrams and one table. Each one: what a box means, what an arrow means, what to include, what to leave out, and when it is the wrong picture. The dots say how often you will actually draw it — ●●● most weeks, ●●○ sometimes, ●○○ rare.

Say the name, not the code.

The codes A1…F5 and the six families are local shorthand for this page only. Nobody outside it uses them. Each card’s grey sub-line gives the name other people will recognise — say “a C4 container diagram” or “a sequence diagram”, never “an A2”. Where a type has no agreed name, the sub-line says so.

The question picks the type. You do not pick it.

Write the question in one sentence first. The verb names the family: is → structure · runs → deployment · happens → behaviour · comes from → data · ships → delivery · owns → business. If the sentence needs the word “and”, you have two diagrams.

A · Structure — what exists 7 types

Static shape. No time, no order. The question is always some form of “what is in there, and what contains what”. Pick one altitude per diagram: a bucket beside a Python function is the most common beginner error on this page.

A1 · System context

●●●

System context diagram · C4 level 1

Box is
A whole system, or a kind of person
Arrow is
“uses” or “sends data to”, in plain words
Size
1 system, 3–7 around it

Include your system as one box · every human role · every external system · one label per arrow.

Leave out everything inside your system. That restraint is the type.

Use when the reader has never heard of the system.

Not when they already know what it is for.

A2 · Container

●●●

Container diagram · C4 level 2

Box is
A separately deployable thing, or a store
Arrow is
A call, with protocol and payload
Size
4–10 boxes

Include each deployable · each store · the technology in small type · the protocol on each arrow.

Leave out modules and classes. If orders.pricing appears, you slipped to A3.

Use when you plan a deployment, estimate cost, or hand over to ops.

Not when the question is how the code is organised.

Close, but not this: vendor icons and an account boundary make a diagram B1.

A3 · Component

●●○

Component diagram · C4 level 3

Box is
A module inside one container
Arrow is
A call between modules
Size
5–12 boxes

Include the modules of one deployable only · the one or two external things they reach.

Leave out other containers’ internals. Two containers mean two diagrams.

Use when you explain how one deployable is built, or where a change lands.

Not when you have over ~12 modules. Group them first. Simon Brown advises most teams stop at level 2 — a component diagram changes with nearly every commit.

Not this: deployable boxes with arrows numbered for time. That is a C4 dynamic diagram — see C2.

A4 · Class / code

●○○

Class diagram · UML · C4 level 4

Box is
A class: name, attributes, methods
Arrow is
Inherits (hollow triangle), uses, or holds

Include only the classes in the relationship you are explaining · the cardinality on an association.

Leave out getters, setters and every class that is merely nearby.

Use when an inheritance or composition tree is genuinely hard to read in code.

Not when the code reads fine — which is nearly always. It rots the day someone renames a method.

A5 · Layered / tiered

●●●

Layered architecture diagram · ArchiMate layered viewpoint

Band is
A layer. Order is the content
Arrow is
The one legal direction of dependency

Include every layer, in order · the rule that says which way imports may point · the one or two legal exceptions, named.

Leave out individual calls. This type states a rule, not a flow.

Use when you onboard someone to a codebase, or you want to stop a bad import.

Not when the layering is aspirational. Draw what is true, or the diagram lies.

A6 · Package & dependency graph

●●○

Package diagram · UML · dependency graph

Box is
A package or module
Arrow is
“imports” — never a call at runtime

Include every package in the scope you are checking · cycles, marked so they stand out.

Leave out the standard library and third-party packages. They are never the problem.

Use when you hunt a cycle, plan a split, or check a layering rule holds.

Not when you would draw it by hand. Generate it, or it is stale by Friday.

A7 · Composite structure

●○○

Composite structure diagram · UML

Box is
One classifier, with its internal parts
Port
A port — a named interface

Include the parts inside one thing · the ports on its boundary · the connectors between them.

Leave out anything outside the classifier. Its surroundings belong on A1 or A2.

Use when ports and adapters are the design — embedded work, or a strict hexagonal codebase.

Not when A3 would do. Almost always, A3 will do.

Three more C4 types. The C4 deployment diagram is carded as B1. Two are not carded: a system landscape diagram shows several systems and how they relate — one level above A1, for an organisation rather than a system. A dynamic diagram is C4’s own notation for a numbered runtime flow drawn over the boxes of A2 or A3, so it answers the same question as C1 or C2 in a different style: A2 boxes, C2 arrows. All three are defined by the C4 model alongside its four levels.

B · Deployment — where it runs 3 types

Boxes are infrastructure, not code. The defining limit: one service is one icon. If your point is a distinction inside a service, no diagram in this family can carry it — use A3 or C3 instead.

B1 · Deployment / infrastructure

●●●

Deployment diagram · UML · C4 deployment

Box is
A managed service or machine, in the vendor’s own icon
Arrow is
A call across infrastructure
Boundary
Account, region, tenant — where billing or trust changes

Include every service on the bill · account and region boundaries · what crosses each boundary.

Leave out services you never think about — IAM, CloudFormation. On every diagram, so they inform none.

Use when the question is cost, ops, blast radius, or “what do we run”.

Not when the point is a rule inside one service. An icon cannot show it.

B2 · Network topology

●●○

Network topology diagram

Box is
A subnet, a gateway, or a host
Line is
A route, or a rule that blocks one

Include CIDR ranges · which subnet is public · every rule that blocks or allows traffic · the egress path.

Leave out applications. What runs on a host belongs on B1.

Use when you run inside a VPC, or a security review asks what can reach what.

Not when you are fully serverless with no VPC — then there is nothing to draw.

B3 · Environment promotion

●●○

No standard name — usually drawn as part of a deployment pipeline

Box is
One environment
Diamond is
A gate: who approves, and on what

Include every environment · what data each holds · every gate and who owns it · what is not promoted (config, secrets).

Leave out the build steps. Those are E1.

Use when an auditor asks how code reaches production, or a release keeps surprising people.

Not when you have one environment. Many teams fold this into the deployment pipeline (E1) rather than drawing it separately.

C · Behaviour — what happens 8 types

Time is in the picture. Each type puts it somewhere different: down a lifeline (C1), along an arrow (C3), as a numbered label (C2), or on an axis (C6). Behaviour diagrams say nothing about structure — if a reader needs to know what contains what, they need a family A diagram too.

C1 · Sequence

●●●

Sequence diagram · UML

Box is
A participant, across the top
Line down
Its lifeline. Time runs down
Arrow is
One message, left or right

Include every participant that sends or receives · one row per message, in order · the reply when it matters · the condition on a branch.

Leave out structure. Stop at about 12 messages.

Use when order is the content: a handshake, a token exchange, a retry, a race.

Not when the reader needs to know what the system is.

C2 · Communication

●○○

Communication diagram · UML · “collaboration” in UML 1.x

Box is
A participant, placed anywhere
Arrow is
A message, numbered for order

Include the same messages a sequence diagram would carry, numbered.

Leave out more than about 8 messages. Without lifelines, order gets hard to follow fast.

Use when who-talks-to-whom matters more than exact ordering, and the topology is not a line.

Not when C1 fits. It almost always fits, and it reads faster.

Example: a checkout request as three numbered steps (client, API, store), solid = call, dashed = reply, boxes placed by where they run. C4 calls this a dynamic diagram.

C3 · Activity / flowchart

●●●

Activity diagram · UML · flowchart

Box is
A step the code takes
Diamond is
A decision, every exit labelled
Arrow is
“next”

Include every branch that changes the outcome · terminal states named (404, 200) · lanes when two entries share a tail.

Leave out who owns each step. A flowchart has no owners — if you need them, use C8. A dashed box may say where a step runs; that is a boundary, not an owner.

Use when the logic is the content — an authorisation check, a validation chain.

Not when nothing branches. A straight line of six steps is a list.

Example: a dashed box around API Gateway shows that the 401 happens there, before your code runs.

C4 · State machine

●●○

State machine diagram · UML · statechart

Box is
A state the thing can be in
Arrow is
A transition, labelled with its event

Include every state · the start state · the terminal states · the guard on a conditional transition.

Leave out the implementation. States are observable facts, not functions.

Use when one thing has a lifecycle with rules.

Not when the thing has two states. A sentence does that better.

Example: a password-reset token — issued, then used or expired.

C5 · Use case

●○○

Use case diagram · UML

Ellipse is
A goal a user has
Stick figure
An actor — a role, not a person
Box is
The system boundary: what is in scope

Include every actor · every goal in scope · the boundary line, which is the real content.

Leave out steps, screens and order. A use case is a goal, not a flow.

Use when you negotiate scope with a stakeholder and need “in” and “out” on one page.

Not when you have a backlog. User stories carry the same facts and stay current.

C6 · Timing

●○○

Timing diagram · UML

Track is
One participant’s state over time
Step is
A change of state at an instant
Axis is
Real time, shared by every track

Include every participant whose timing interacts · the real durations · the constraint you are proving (“under 60 s”).

Leave out anything untimed. If no deadline matters, this type has no content.

Use when a deadline, a timeout or a race is the design problem.

Not when order alone is the point. C1 says that with far less machinery.

C7 · Interaction overview

●○○

Interaction overview diagram · UML

Node is
A whole sequence diagram, referenced by name
Diamond is
Which sequence runs next

Include only the ref frames and the decisions between them.

Leave out the messages themselves. They live in the diagram each frame points at.

Use when you have five or more sequence diagrams and need an index showing which runs when.

Not when you have three. A sentence links them better.

C8 · Swimlane / BPMN

●●○

BPMN process diagram · swimlane · cross-functional flowchart

Lane is
Who does it — a team, a role, a system
Box is
A step that lane performs
Crossing
A handover — the thing this type exists to expose

Include one lane per actor · every step in its owner’s lane · every handover · the waits, if the process is slow.

Leave out technical calls. A lane is a who, not a service.

Use when a process crosses teams and nobody agrees who owns which step.

Not when one team does everything. Then C3 is simpler.

D · Data — what it holds and where it came from 6 types

An arrow here means data moved, never that something was called. That single rule separates this family from C, and mixing the two is the most common error in data diagrams.

D1 · ERD

●●○

Entity–relationship diagram · ERD · crow’s-foot notation

Box is
A table or entity, with its key columns
Line is
A relationship; the foot marks cardinality

Include primary and foreign keys · cardinality on every line · the columns that carry meaning.

Leave out every column. Audit timestamps on 30 tables teach nothing.

Use when you design a schema, or explain a join someone keeps getting wrong.

Not when the data is one document per key, as in a key-value store. There are no relationships to draw.

D2 · Dimensional / star schema

●●○

Dimensional model · star schema · Kimball

Centre is
The fact table: measures and foreign keys
Point is
A dimension: how you slice it

Include the grain of the fact table, stated in words · every dimension · the measures.

Leave out staging and raw tables. This type describes the model, not the pipeline — that is D5.

Use when you design a warehouse or a BI layer, and “what can I group by” is the question.

Not when you are modelling transactions. Use D1.

D3 · Data flow diagram

●●○

Data flow diagram · DFD · the STRIDE threat-model shape

Circle is
A process that transforms data
Open bars
A data store
Dashed line
A trust boundary — where the threats live

Include every flow crossing a boundary, labelled with what data · every store · the external entities.

Leave out order and timing. Nothing here says “first”.

Use when you threat-model. Every STRIDE method starts by drawing this.

Not when you want control flow. An arrow here means data moved, not that something was called.

D4 · Lineage

●●○

Data lineage diagram

Box is
A source or an output
Line is
One feed: this field reaches that output

Include every feed that exists today · the ones you propose to cut, drawn differently · the field names when the question is field-level.

Leave out the machinery that moves the data. That is D5.

Use when someone asks “where did this number come from?”, or you argue to remove a dependency.

Not when there are more than ~30 feeds. Past that it is a hairball — filter to one output.

D5 · Pipeline DAG

●●○

Directed acyclic graph · DAG · workflow diagram

Box is
A task
Arrow is
“must finish before”

Include every task · the fan-out width (how many run at once) · retries and the failure path, if they differ per task.

Leave out the data shape. What flows is D4; what runs is here.

Use when a job has parallelism, a join, or a step people keep running out of order.

Not when the pipeline is a straight line. Write the six commands instead.

Example: a nightly sales report — load the orders, total each region in parallel, then merge.

D6 · Matrix

●●○

Access matrix / responsibility grid · a table, not a diagram

Row is
A role, or a kind of person
Column is
A field, or an action
Cell is
One value: allowed, masked or denied

Include every role · every field or action the question covers · a legend for each cell value · the default for anything not listed.

Leave out arrows and order. How a request reaches the check is C1 or C3.

Use when a reviewer must check the rows one at a time — who reads which field, or who owns which task.

Not when the content has a shape: what calls what, or what happens first. Draw that instead.

A responsibility grid (RACI) is the same table: tasks down the side, people across the top.

E · Delivery & operations — how it ships and how it breaks 3 types

These describe the machinery around the system rather than the system. They go stale faster than anything else on this page, so keep them small and date them.

E1 · CI/CD pipeline

●●○

Deployment pipeline · Humble & Farley · “CI/CD pipeline”

Box is
A stage
Diamond is
A gate: automatic or human
Red path
What happens on failure

Include every stage · every gate and who owns it · the failure path · roughly how long each stage takes.

Leave out the environments. Those are B3 — one shows stages, the other shows targets.

Use when onboarding, or when the pipeline has a gate people do not know about.

Not when it is push-to-deploy with no gates. One sentence covers it.

E2 · Event-driven architecture

●●○

Event-driven architecture diagram · pub/sub topology

Bar is
A topic or queue
Box is
A producer or a consumer
Arrow is
Publish, or subscribe

Include every topic by its real name · each consumer group · the dead-letter queue · ordering and delivery guarantees, in small type.

Leave out request/response calls. Those belong on A2 — mixing them hides which paths are asynchronous.

Use when the system is event-driven and nobody can list who consumes what.

Not when you have no broker.

E3 · Incident / runbook flow

●○○

No standard name — an activity diagram used as a runbook

Box is
An action the responder takes
Diamond is
A check, with a real threshold

Include the alert that starts it · real numeric thresholds · who to page, by role · the stop condition.

Leave out the architecture. At 3 a.m. nobody wants to read a component diagram.

Use when an alert is noisy, or a new on-call rotation starts.

Not when the response is “read the dashboard and think”. A diagram cannot help there.

F · Business & strategy — why it is shaped this way 5 types

Boxes here are not code. They are domains, capabilities or steps in a value chain. These diagrams are for deciding where to invest, not for building — and they age in quarters, not sprints.

F1 · Context map

●●○

Context map · domain-driven design · Evans

Blob is
A bounded context — a model with its own language
Line is
A relationship pattern, named

Include every context · who is upstream (U) and downstream (D) · the integration pattern on each link · the team that owns each context.

Leave out services and databases. A context is a model, not a deployment.

Use when several teams share concepts and the word “customer” means different things to each.

Not when one team owns one domain. You have one context.

F2 · Capability map

●○○

Business capability map · ArchiMate · BIZBOK

Box is
A capability — something the business can do
Nesting is
Level 1 contains level 2
Shading is
Investment, maturity, or pain

Include capabilities as nouns (“order fulfilment”), not teams or systems · two levels at most · one shading scale, with its key.

Leave out arrows. A capability map has no flow — if you draw arrows, you wanted F3.

Use when you argue for budget and need to show where a system sits in the business.

Not when engineers are the audience. It tells them nothing they can act on.

F3 · Value stream map

●○○

Value stream map · two different senses — see below

Box is
A step someone performs
Low line
Waiting
High line
Working

Include real measured times for both work and wait · the total of each · who performs each step.

Leave out estimates. A value stream map built on guesses proves whatever you already believed.

Two senses, one name. The Lean/Toyota one is drawn here: material and information flow, hunting waste. TOGAF and ArchiMate use value stream for the end-to-end activities that create value, named from the recipient’s side. Say which you mean.

Use when a process is slow and you need to show that the delay is queueing, not effort.

Not when you have no measurements yet. Measure first.

F4 · Wardley map

●○○

Wardley map · Simon Wardley

Up is
Closer to the user’s need
Right is
More evolved: genesis → commodity
Line is
“depends on”

Include the user need at the very top · every component the chain depends on · its honest position on the evolution axis.

Leave out time. The horizontal axis is maturity, not a schedule — the single most common misreading.

Use when you argue build versus buy, and you want to show that something is now a commodity.

Not when the audience has not seen one before. It needs ten minutes of explanation.

F5 · Object diagram

●○○

Object diagram · UML

Box is
One instance, with real values
Line is
A link that exists at this instant

Include concrete values · the instance names, underlined · only the objects in the case you are explaining.

Leave out anything general. If you write a type without a value, you wanted A4.

Use when a class diagram is correct and still confusing, and one worked example would settle it.

Not when a JSON snippet would do. It usually would.

Framework crosswalk

No framework defines “all the types”. Three try, and they overlap. This page is organised by the question you are asking, which is why it matches none of them exactly.

FrameworkDefinesWhat it covers, in this page’s terms
C4 Simon Brown4 levels A1, A2, A3, A4, plus B1 (its deployment diagram) and the dynamic diagram (C2 drawn over A2 or A3 boxes). Nothing about data or delivery. The best starting point.
UML 2.514 types 7 structural (A4, F5, A6, A3, A7, B1, profile) and 7 behavioural (C5, C3, C4, C1, C2, C7, C6). Formal and complete; mostly unused outside enterprise work. The only one here this page omits is the profile diagram, which describes UML itself.
4+1 views Kruchten5 views Logical (A3), process (C1, C3), development (A5, A6), physical (B1), plus scenarios that tie them together. A way to decide which diagrams a system needs — not a type itself.
ArchiMate 3 The Open Group26 viewpoints The enterprise-architecture standard, and the one this page leaned on without naming it. Its strategy layer defines F2 (capability map) and F3 (value stream) as formal viewpoints; its layered viewpoint is A5; its business, application and technology layers cover A2 and B1. Use its vocabulary when the audience is an enterprise architect.
arc4212 sections A documentation template, not a diagram language. Its sections 3, 5, 6 and 7 ask for A1, A3, C1/C3 and B1 respectively.

Three mistakes, all from the wrong type

  1. Structure drawn as sequence. The arrows are numbered 1 to 9, and the reader still cannot say what the system contains. Order is not shape. Draw both, separately.
  2. Two altitudes in one picture. A bucket beside a Python function. The reader cannot tell which boxes are peers, so they trust none of them.
  3. A deployment diagram asked to carry a policy. Icons name services. A rule about which route needs a token lives in A3 or C3, never in an icon.

What rarely earns a diagram

A linear process with no branchWrite the list.
A thing with two statesWrite the sentence.
Error handling that is the same everywhereSay so once, in prose.
Anything a table states more preciselyA figure carries shape; a table carries detail.
Anything a tool can generate from the codeGenerate it. A hand-drawn dependency graph is stale by Friday.

The two checks that catch most problems

1 · Can you state the question in one sentence, without “and”?If not, split the diagram.
2 · Does any visual property carry two meanings?Dashed cannot mean both “reply” and “optional”. Pick one, and use a second property for the other.

What is standard here, and what is not. The types are standard: UML 2.5 defines 14 of them (7 structural, 7 behavioural); C4 defines levels 1–4 plus a system landscape, a deployment and a dynamic diagram; Kruchten’s 4+1 defines the five views; ArchiMate 3 defines 26 viewpoints including the capability map and value stream; DFD shapes follow the STRIDE threat-modelling convention. The grouping is not standard: the six families and the codes A1…F5 are this page’s own, built around the question you are asking rather than around any one framework. Two cards say “no standard name” because none exists.
